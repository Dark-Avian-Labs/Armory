1. Executive Summary

This audit covered the full Armory repository: the Express server (auth, routers, DB layer, import pipeline, scraping, caching, session handling), the React client, shared modules, and configuration. All findings below were verified by reading the actual code; line numbers refer to the state of the repository on 2026-08-31.

Overall assessment: the codebase is in very good shape. No Critical or High severity issues were found. Every SQL statement uses parameterized queries (dynamic identifiers only ever come from compile-time whitelists), share-token access uses timing-safe comparison with 404-on-denial semantics exactly as documented in AGENTS.md, external fetching is protected by a host allowlist with private-IP DNS checks and DNS pinning, CSRF protection is layered (synchronized token + Origin check + Sec-Fetch-Site), Clerk webhooks are signature-verified, admin routes are consistently gated, and committed env files are dotenvx-encrypted with the private key correctly gitignored. TypeScript hygiene is exceptional — the repository contains zero as any, @ts-ignore, or @ts-expect-error occurrences.

The single Medium finding is a reliability gap: the cross-process import lease is never renewed during a running import, so a legitimately slow import (> 30 minutes) can have its lease expire and be stolen by a second process, allowing two imports to write the catalog concurrently. The remaining findings are Low/Informational hardening opportunities: a path-traversal defense-in-depth gap when writing export files named by the remote manifest, a Clerk API fan-out that anonymous requests can trigger, and assorted consistency, performance, and UX polish items.

2. Security Findings (2 Low, 4 Informational)

LowDone SEC-1: Export download writes files using unsanitized manifest-derived names (path traversal defense-in-depth gap)

server/import/pipeline.ts:76-81, 154-157  ·  server/import/manifest.ts:98-119
Description
The import pipeline parses DE's remote manifest and derives entry.category as the filename portion before the first .. That value is then joined into the exports directory and written to without any separator/traversal sanitization. A manifest line such as ExportWeapons/../../evil!hash yields a category that passes the REQUIRED_EXPORTS.some((req) => e.category.startsWith(req)) filter (it contains no dot, so the whole string becomes the category) and resolves outside data/exports/. 
// server/import/pipeline.ts
const entry = needed[i];
const url = `${CONTENT_BASE_URL}${entry.fullFilename}`;
const localFilename = `${entry.category}.json`;
const localPath = path.join(EXPORTS_DIR, localFilename);   // no sanitization
const hashPath = path.join(EXPORTS_DIR, `${entry.category}.hash`);
...
fs.writeFileSync(tmpPath, text, 'utf-8');
fs.renameSync(tmpPath, localPath);
Impact
Arbitrary file write outside the exports directory — but only if the upstream manifest at origin.warframe.com were compromised or spoofed. TLS, the fetch host allowlist, and the required-prefix filter make this remote-only in practice, hence Low. Notably, the sibling image pipeline (server/import/safeImagePath.ts) does sanitize segments and asserts the resolved path stays under the images root, so this file-write path is the one place external names reach the filesystem unsanitized.
Recommendation
Run entry.category (and fullFilename when building the URL path) through the same segment sanitizer used for images, or assert the resolved localPath/hashPath stay under EXPORTS_DIR analogous to assertUnderImagesRoot().

LowSEC-2: Anonymous requests can trigger Clerk Backend API fan-out (cost/quota amplification)

server/auth/armoryUsers.ts:66, 152-181  ·  server/routes/buildsRouter.ts:212, 233
Description
Public, unauthenticated endpoints (GET /api/builds/by-equipment, GET /api/users/:username/builds, GET /api/builds/by-user) call resolveOwnerUsernames(), which performs live clerkClient.users.getUser() calls for every owner id missing from the local armory_users cache — up to CLERK_FANOUT_MAX_PER_REQUEST = 25 per request. 
// server/auth/armoryUsers.ts
const CLERK_FANOUT_MAX_PER_REQUEST = 25;
...
const toSync = missing
  .filter((id) => (clerkSyncCooldown.get(id) ?? 0) <= now)
  .slice(0, CLERK_FANOUT_MAX_PER_REQUEST);
await Promise.all(toSync.map(async (clerkUserId) => { ... getUser ... }));
Impact
An anonymous client can cause up to 25 upstream Clerk API calls per request (within the 600-requests/15-min API rate limit), consuming Clerk quota and adding latency. The 5-minute per-user cooldown and 2000-entry cap bound the damage substantially, which is why this is Low rather than Medium.
Recommendation
Consider a global (not per-user) concurrency/budget cap on Clerk sync calls per time window, or defer username resolution for anonymous requests to a background refresh so request handling never fans out.

InformationalDone SEC-3: Secondary share-token comparison is not timing-safe

server/routes/loadoutsRouter.ts:126-129
Description
Primary access checks use timingSafeEqualString() (server/loadoutAccess.ts:31), but the follow-up flag that reveals linked builds via loadout-token access uses plain ===: 
const hasLoadoutTokenAccess =
  vis === 'unlisted' &&
  readContext.shareToken != null &&
  loadoutAccessRow.share_token === readContext.shareToken;
Impact
Not practically exploitable: for a non-owner to reach this line, canReadLoadout() must already have passed with a timing-safe match of the same token, so the plain comparison only re-checks a known-equal value. Flagged for consistency only.
Recommendation
Use timingSafeEqualString() here as well, keeping one comparison idiom for all token checks.

InformationalSEC-4: CSP permits 'unsafe-inline' styles

server/http/helmetCsp.ts:24
Description
The Helmet CSP is otherwise tight (self-only scripts plus Clerk FAPI and Cloudflare challenges), but style-src includes 'unsafe-inline':

Impact

Recommendation

InformationalSEC-5: Overframe fetching via cuimp bypasses the DNS-pinned fetch stack

server/http/fetchOverframe.ts:29-41, 85-103  ·  server/http/fetchWithTimeout.ts:11-26
Description
All other external fetches go through fetchWithTimeout() with assertAllowedFetchUrl() (host allowlist, private-IP DNS resolution checks, DNS pinning agent). Overframe scraping instead uses the cuimp browser-impersonation client to get past Cloudflare. It re-validates HTTPS and restricts hosts to overframe.gg / media.overframe.gg (toAbsoluteOverframeUrl), but does not perform the private-IP resolution checks, and OVERFRAME_PROXY can redirect this traffic through an arbitrary proxy.
Impact
Very limited: hostnames are hard-pinned to Overframe, so exploiting this would require DNS control over overframe.gg or control of the server's environment variables. Also note cuimp itself is a TLS-fingerprint impersonation dependency (see BP-4). The Overframe scrape is force-only per AGENTS.md, further shrinking exposure.
Recommendation
Document the divergence; optionally add a resolved-IP privacy check before the cuimp request for parity.

InformationalDone SEC-6: Unbounded ability_names IN-list from query string

server/routes/catalogRouter.ts:336-349  ·  server/routes/abilitiesListQuery.ts:5-9
Description
GET /api/abilities?ability_names=a,b,c… splits the parameter with no cap on element count and builds one ? placeholder per name. The list is bounded only by the HTTP request-line size. 
whereSql: `unique_name IN (${abilityNames.map(() => '?').join(',')})`,
Impact
Worst case is a caught SQLite error (too many variables) returning 500, and some wasted work under the 600-req/15-min rate limit. Also note each distinct name list becomes a distinct response-cache key (cacheKey = `abilities:…`), though the cache is capped at 256 entries with eviction. No data exposure.
Recommendation
Cap the list (e.g. .slice(0, 50)) and reject oversized requests with 400.

3. Reliability Findings (1 Medium, 1 Low, 2 Informational)

MediumDone REL-1: Import lease is never renewed; long imports can exceed the 30-minute TTL and be stolen

server/import/importRuns.ts:183-213, 283-293  ·  server/import/startupPipeline.ts:196-218
Description
tryAcquireImportLease() stamps acquired_at once; nothing updates it while the pipeline runs. Any other process calling isImportLeaseHeld() → releaseStaleImportLease() after IMPORT_LEASE_TTL_MINUTES = 30 will clear the lease and mark the still-running run as failed, and a new import can then acquire it. 
const IMPORT_LEASE_TTL_MINUTES = 30;
...
WHERE id = ?
  AND (
    lock_token IS NULL
    OR acquired_at IS NULL
    OR acquired_at <= datetime('now', '-30 minutes')
  )
A full run (export downloads, thousands of image fetches at 60s timeout each, Overframe/wiki scrapes) can plausibly exceed 30 minutes on a slow network. Within one process the in-memory activeJobPromise guard prevents overlap, but across processes — e.g. the server's admin import plus a pnpm run data:import CLI run (runManualImport uses the same lease) — two imports could write the catalog concurrently after TTL expiry.
Impact
Concurrent catalog writes (interleaved table rebuilds, image-path restores), spurious "Interrupted by server restart or stale import lock" failures on a run that is actually still progressing, and confusing admin state. SQLite WAL prevents corruption, but data consistency between steps is not guaranteed.
Recommendation
Add a lease heartbeat: periodically UPDATE import_lease SET acquired_at = datetime('now') WHERE lock_token = ? from the running job (e.g. from the reporter callback or a timer), and/or raise the TTL well above worst-case run duration.

LowDone REL-2: Admin "reset import lock" force-releases the cross-process lease with only an in-process running check

server/import/adminImportJob.ts:156-178  ·  server/routes/catalogRouter.ts:505-519
Description
resetAdminImportLock() refuses only when this process has an active job (activeJobPromise !== null), then unconditionally calls forceReleaseImportLease(). An import running in a different process (CLI data:import) holds the same DB lease but is invisible to this check, so an admin can clear its lease mid-run and start a competing import. 
export function resetAdminImportLock(): AdminImportResetResult {
  if (activeJobPromise !== null) {
    return { cleared: false, reason: '...still running in this process...' };
  }
  forceReleaseImportLease();   // clears lease regardless of other processes
Impact
Same concurrent-write consequences as REL-1, but requires a deliberate admin action, hence Low. (Codex's equivalent documents the same refusal semantics — "refused while an in-process sync is still running" — so this matches the documented design, but the cross-process hole is worth noting.)
Recommendation
Before force-release, check lease freshness (acquired_at recency) and warn/require a second confirmation when the lease looks actively held rather than stale.

InformationalREL-3: Any unhandled promise rejection shuts down the whole server (deliberate crash-fast policy)

server/index.ts:442-447
Description
process.on('unhandledRejection', (reason) => {
  log('error', 'Unhandled promise rejection; shutting down', {...});
  shutdown(1);
});
This is a sound crash-fast choice and the shutdown path is graceful (waits for admin import, closes DBs). It does mean a single stray rejection in any background task takes down request serving. The import pipeline wraps every step in try/catch, so no such path was found — flagged purely so the trade-off stays a conscious one.
Impact
Availability depends on process supervision (restart-on-exit) being configured in deployment.
Recommendation
No change needed; ensure the production process manager restarts on exit code 1.

InformationalREL-4: Client/proxy caching can serve stale catalog data for up to 5 minutes after admin edits

server/cache/catalogResponseCache.ts:11-14, 50-51  ·  server/routes/catalogRouter.ts:484
Description
Catalog endpoints send Cache-Control: public, max-age=300. The admin artifact-slot PATCH calls bustCatalogResponseCache(), which clears the server cache immediately — but browsers/CDNs may keep the previous payload for up to 5 minutes without revalidating the ETag.
Impact
Admins may not see their own polarity edits reflected immediately in catalog lists. Cosmetic.
Recommendation
Acceptable; if it bothers admins, use no-cache + ETag (revalidate every time) instead of max-age=300.

4. Best Practices Findings (4 Low)

LowBP-1: Inconsistent input-validation styles across write endpoints

server/routes/buildsRouter.ts:42-49 vs 535-549  ·  server/routes/loadoutsRouter.ts:190-200, 249-267
Description
POST /builds validates the body with a zod schema (BuildCreateBodySchema), while PUT /builds/:id and the loadout create/update handlers hand-roll field checks (typeof name !== 'string', manual trim/length checks, and a literal 255 in loadoutsRouter.ts:252 instead of MAX_NAME_LENGTH). 
// loadoutsRouter.ts:252 — magic number duplicates MAX_NAME_LENGTH
if (typeof name !== 'string' || name.trim().length === 0 || name.trim().length > 255) {
Impact
No security hole found (all fields are ultimately validated), but the two styles can drift — the hard-coded 255 already bypasses the shared constant.
Recommendation
Define zod schemas for the update payloads too, reusing MAX_NAME_LENGTH / MAX_DESCRIPTION_LENGTH.

LowBP-2: Mixed logging — structured JSON logger vs raw console.log in the same subsystems

server/logger.ts  ·  server/db/queries.ts (8×)  ·  server/import/manifest.ts (4×)  ·  server/import/images.ts, pipeline.ts, others
Description
Request-path code consistently uses the structured log() helper (JSON lines with request IDs), but the import/DB layer mixes in ~35 bare console.log calls (e.g. [DB] Processed …, [Import] Manifest saved …).
Impact
Log aggregation sees a mix of JSON and plain-text lines from one process, complicating parsing and level-based filtering.
Recommendation
Route pipeline output through log() (or the existing reporter callback) so production logs stay uniformly structured.

LowBP-3: Monolithic client components (ModBuilder is ~91 KB in one file)

client/components/ModBuilder/ModBuilder.tsx (~91 KB, ~2,600 lines)  ·  client/components/Share/BuildShareModal.tsx (~48 KB)  ·  client/components/BuildOverview/BuildOverview.tsx (~42 KB)
Description
ModBuilder.tsx combines equipment loading, save/favorite flows, PiP window management, compare snapshots, toasts, and layout in a single component. Some state is already extracted (hooks/useModBuilderState.ts), but the main file remains the largest by far in the repo.
Impact
Harder review/maintenance, and broad state colocation means many state changes re-render the entire builder tree (see PERF-3).
Recommendation
Continue the extraction already started: move PiP, compare, and save-modal logic into hooks/subcomponents with memoized boundaries.

LowBP-4: Dependency risks — @types/better-sqlite3 major-version lag and the cuimp scraper dependency

package.json:33 (better-sqlite3 ^13.0.3), :58 (@types/better-sqlite3 ^9.6.0), :39 (cuimp ^2.1.1)
Description
The type stubs for better-sqlite3 are four majors behind the runtime package, so new v13 API surface is untyped or mistyped. Separately, cuimp (curl-impersonate wrapper used to evade Cloudflare bot detection for Overframe, server/http/fetchOverframe.ts) downloads/executes an external binary and by nature breaks whenever Cloudflare or Overframe changes posture — a fragile, ToS-gray dependency, though the code degrades gracefully (import step fails with a clear message; the rest of the pipeline continues).
Impact
Type-safety gaps around DB calls; operational fragility of a force-only import step.
Recommendation
Bump @types/better-sqlite3 to match v13 (or adopt the package's own types if available). Keep cuimp isolated as it is; no further action needed while the Overframe step stays force-only.

5. Performance Improvements (1 Low, 2 Informational — secondary category)

LowPERF-1: Public-build discovery queries scan without a visibility-oriented index, and /builds/catalog is uncached

server/routes/buildsRouter.ts:120-141 (catalog), 184-210 (by-equipment)  ·  server/db/userSchema.ts:67-78
Description
GET /api/builds/catalog runs a full GROUP BY over all public builds on every request with no response caching (catalog-DB endpoints get sendCachedCatalogJson; this user-DB endpoint does not). The existing indexes are (clerk_user_id), (clerk_user_id, visibility), and (equipment_type, equipment_unique_name) — none lead with visibility, and the discovery sort (ORDER BY updated_at DESC) always sorts in memory. 
SELECT equipment_type, equipment_unique_name, COUNT(*) AS build_count
FROM builds WHERE visibility = 'public'
GROUP BY equipment_type, equipment_unique_name ...
Impact
Negligible at current scale (≤ 250 builds/user), but this is the main anonymous browse path and will degrade linearly with total builds.
Recommendation
Add a partial index, e.g. CREATE INDEX idx_builds_public_discovery ON builds(equipment_type, equipment_unique_name, updated_at) WHERE visibility = 'public', and/or give /builds/catalog a short-TTL response cache.

InformationalPERF-2: Image-path DB update runs 6 blind UPDATEs per item across unrelated tables

server/import/images.ts:210-240
Description
updateDbImagePaths() executes an UPDATE against all six catalog tables for every unique name (~6× the necessary statements, most matching zero rows), inside one transaction.
Impact
Import-time only; adds seconds, not user-facing latency.
Recommendation
Optional: record each manifest entry's owning table when collecting names, then update only that table.

InformationalPERF-3: /api/mods search filters the full cached list in JS per request, and lacks the ETag caching other catalog endpoints have

server/routes/catalogRouter.ts:244-274  ·  server/cache/modListCache.ts
Description
The mod list is cached for 15 min per filter combination (good), but each request with search= linearly re-filters the whole deduped array, and the endpoint returns no ETag/Cache-Control, unlike the endpoints using sendCachedCatalogJson.
Impact
Minor CPU per request; mod catalog is a few thousand rows, so this is cheap today.
Recommendation
Optional: add ETag support to /api/mods responses for client-side revalidation wins.

7. Positive Observations

Things this codebase does notably well — verified during the audit.

  • SQL injection: effectively eliminated. Every user-reachable query is parameterized; the only template-string SQL fragments are compile-time constants or whitelisted table names (resolveArtifactSlotsTable, ALLOWED_TABLE_NAMES in resetCatalogData.ts, IMAGE_PATH_TABLES).
  • Layered CSRF defense (server/index.ts:157-221): csrf-sync synchronized tokens, plus an Origin-vs-Host check, plus Sec-Fetch-Site: cross-site blocking — and the client (client/utils/api.ts) transparently injects tokens and retries exactly once on token rotation.
  • Serious SSRF hardening (server/http/allowedFetchHosts.ts, fetchWithTimeout.ts): HTTPS-only host allowlist, private/loopback IP rejection for every resolved A/AAAA record, a DNS-pinning undici agent to defeat rebinding, redirect: 'error', per-type byte limits with streaming enforcement, and image MIME validation.
  • Decompression-bomb protection: the LZMA manifest decoder checks the declared size and enforces a 64 MB output cap during streaming decompression (server/import/manifest.ts:60-96).
  • Share-token model done right: 24-byte randomBytes base64url tokens, unique-indexed, timing-safe comparison, denied reads return 404 (never 403), tokens only serialized to owners/admins, and the documented loadout-token → linked-builds reveal is implemented exactly as specified in AGENTS.md.
  • Path traversal defenses on the image pipeline: safeImagePath.ts sanitizes segments, rejects absolute/dot segments, and asserts the resolved path stays under the images root — with dedicated tests.
  • Secrets hygiene: committed .env.production/.env.development are dotenvx-encrypted, .env.keys is gitignored (verified), placeholder/still-encrypted Clerk keys fail fast at boot, and production enforces SESSION_SECRET ≥ 32 chars, webhook secret presence, and TRUST_PROXY/SECURE_COOKIES coupling.
  • Clerk webhooks correctly wired: svix signature verification via verifyWebhook, mounted on a raw-body route before JSON parsing, sessions, and CSRF middleware.
  • Admin surface consistently gated: every /api/admin/* route uses requireArmoryAdmin (metadata apps.armory === 'admin' parsed defensively from session claims), import actor IDs are stored hashed and masked in run history.
  • Exceptional TypeScript hygiene: zero as any, @ts-ignore, or @ts-expect-error in the entire repository.
  • Robust import machinery: DB-backed run history, single-flight in-process guard, cross-process lease with startup recovery, atomic tmp-file+rename export writes, JSON validation before replacing files on disk, per-step error containment with a structured summary, and cache busting after runs.
  • Graceful shutdown that waits for a running admin import, disposes timers, and closes all three DBs; health (/healthz) vs readiness (/readyz checks all three DBs) separated correctly.
  • Client XSS posture: no dangerouslySetInnerHTML anywhere; description rendering tokenizes to React elements with URLs restricted to http(s) by regex; user-supplied equipment_image is validated server-side against a relative-path/HTTPS-host allowlist with scheme rejection.
  • Accessibility investment: focus-trapped modal with Escape handling and focus restore, aria-live loading states, sr-only "opens in a new tab" hints, and widespread aria annotations (250+ occurrences across the client).
  • Test coverage of the risky parts: dedicated tests for build/loadout access control, session store, import runs/lease, CSP, safe image paths, mod-config validation, Clerk env normalization, and a large client util test suite.
